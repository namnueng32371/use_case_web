# เกณฑ์การให้คะแนนความสำคัญ (Priority Scoring)

เอกสารนี้อธิบายว่าคะแนนความสำคัญของแต่ละ use case คำนวณมาจากอะไร ใช้ทำอะไร และตั้งใจ**ไม่**เอาอะไรมาผสมด้วยเหตุผลอะไร — สำหรับใครก็ตามที่ต้องอธิบายให้ผู้บริหารฟัง หรือจะแก้สูตรในอนาคต

## สูตร

```
คะแนน = (Impact×0.35 + Feasibility×0.25 + Data×0.25 + (6−Risk)×0.15) × 20
```

ช่วงคะแนนจริง **20–100** (กรอกแย่ที่สุดทุกช่องยังได้ 20) แบ่งระดับความสำคัญเป็น:
- **≥ 75 = สูง**
- **50–74 = กลาง**
- **< 50 = ต่ำ**

น้ำหนัก: Impact 35% (มากสุด), Feasibility กับ Data เท่ากันที่ 25%, Risk 15% (น้อยสุด — เพราะคำนวณแบบกลับด้าน `(6−Risk)` อยู่แล้ว จึงตั้งน้ำหนักต่ำกว่าเพื่อไม่ให้ฉุดคะแนนแรงเกินไป)

## ที่มาของคะแนนแต่ละตัวแปร (ใช้อยู่ปัจจุบัน)

> ตรวจแล้ว 2026-10-12: เว็บ (ทั้ง `artifact.html` และ `AI_Use_Case_Program12.html`) ให้คะแนนย่อย คะแนนรวม ระดับ และจำนวนช่องที่ขาด ตรงกับ Excel จริงทั้ง 34 กรณีทดสอบ (26 กรณีทั่วไป + 8 กรณีเฉพาะของช่องชั่วโมง/มูลค่า) วิธีทดสอบดู AGENTS.md หัวข้อ 7

คะแนน 1–5 ของแต่ละปัจจัย**ไม่ได้ให้คนกรอกเอง** แต่คำนวณจาก dropdown 10 ช่องบังคับ
(ตรงกับ Excel template sheet 1 และ sheet 3 — `computeScoreDetail()` ในทั้งสองไฟล์ HTML)

| ปัจจัย | มาจาก (ชื่อ field / คอลัมน์ sheet 1) | วิธีรวม |
|---|---|---|
| Impact | `timeSpent` (L) · `lossValue` (M) | เฉลี่ยแล้วปัดเศษ — ถ้า `lossValue` เป็น "ประเมินเป็นเงินไม่ได้" (คะแนน `-`) ใช้ `timeSpent` ตัวเดียว |
| Data | `dataFormat` (O) · `dataHistory` (P) · `dataRights` (R) | เฉลี่ยแล้วปัดเศษ |
| Feasibility | `needConnect` (S) · `adminOwner` (T) | เฉลี่ยแล้วปัดเศษ |
| Risk | `aiErrorImpact` (U) · `reviewNeed` (V) · `confidentiality` (W) | เฉลี่ยแล้วปัดเศษ |

- **Impact เมื่อมีแค่ชั่วโมง** (ช่องมูลค่าว่าง หรือเลือก "ประเมินเป็นเงินไม่ได้" ซึ่งไม่นับคะแนน): ใช้คะแนนของช่องชั่วโมงเป็น Impact ตรงๆ ไม่เฉลี่ย ไม่ปัดเศษ — น้อยกว่า 4 ชม. = 1 · 4–10 = 2 · 10–20 = 3 · 20–40 = 4 · มากกว่า 40 = 5 ถ้ามีทั้งสองช่องจะเฉลี่ยแล้วปัดเศษ (เช่น 2 กับ 5 → 3.5 → 4) ข้อสังเกต: case ที่ชั่วโมงน้อยแต่เสียหายสูงและเลือก "ประเมินไม่ได้" จะได้ Impact ต่ำกว่าที่ควร เป็นวิธีที่ออกแบบไว้ตั้งแต่ต้นของ template ไม่ได้เปลี่ยนใหม่
- ถ้าช่องชั่วโมงว่างแต่มีมูลค่า Impact = คะแนนมูลค่าอย่างเดียว (ข้อมูลไม่ครบ จึงไม่มีคะแนนรวม)
- คะแนนของแต่ละตัวเลือกอยู่ใน `DATA_LISTS` (HTML) และ `LISTS` (`docs/build_template.py`) ต้องแก้ให้ตรงกันทั้ง 3 ที่ — ตารางตัวเลือก→คะแนนดูที่ [TEMPLATE_GUIDE.md](TEMPLATE_GUIDE.md)
- ขาดช่องบังคับแม้ช่องเดียว = แสดง **"ข้อมูลไม่ครบ"** แทนคะแนน ไม่เข้าการจัดอันดับ
- คะแนนรวมปัดทศนิยม 1 ตำแหน่ง และ**ไม่ถูกบันทึก** คำนวณสดทุกครั้ง

## ความหมายของคะแนน 1–5 แต่ละตัวแปร (rubric อ้างอิง)

> rubric ด้านล่างมาจากฟอร์มรุ่นเก่าที่ให้คนเลื่อนให้คะแนนเอง ปัจจุบันใช้เป็น**คำอธิบายความหมาย**
> ของระดับ 1–5 ตอนอธิบายผู้บริหาร และเป็นแนวทางตอนตั้งคะแนนให้ตัวเลือก dropdown

### 1. ผลกระทบทางธุรกิจ (Impact) — 35%
| คะแนน | ความหมาย |
|---|---|
| 1 | น้อยมาก — ช่วยงานเล็กๆ ภายในทีมเดียว แทบไม่กระทบรายได้/ต้นทุน/ลูกค้า |
| 2 | น้อย — ช่วยให้สะดวกขึ้นบ้าง ลดงานซ้ำเล็กน้อย แต่วัดเป็นตัวเงินยาก |
| 3 | ปานกลาง — เห็นผลชัดในหน่วยงาน เช่น ประหยัดเวลา/ต้นทุนพอสมควร |
| 4 | สูง — ส่งผลต่อตัวเลขสำคัญของธุรกิจชัดเจน กระทบหลายหน่วยงาน |
| 5 | สูงมาก — เปลี่ยนเกมธุรกิจ กระทบรายได้/ต้นทุน/ความสามารถแข่งขันระดับองค์กรอย่างมีนัยสำคัญ |

### 2. ความเป็นไปได้ทางเทคนิค (Feasibility) — 25%
| คะแนน | ความหมาย |
|---|---|
| 1 | ยากมาก — เทคโนโลยียังไม่พร้อม ทีมไม่มีความเชี่ยวชาญ ต้องวิจัย/ทดลองหนักก่อน |
| 2 | ยาก — พอมีแนวทาง แต่ซับซ้อน ต้องหาคน/เครื่องมือเพิ่ม ความไม่แน่นอนสูง |
| 3 | ปานกลาง — ทำได้ด้วยเทคโนโลยีที่มี แต่ต้องใช้ความพยายาม/เวลาพอสมควร |
| 4 | ทำได้ดี — มีเครื่องมือ/บริการสำเร็จรูปรองรับ ทีมพอมีประสบการณ์ |
| 5 | ง่าย — เทคโนโลยีพร้อมใช้ทันที มีตัวอย่าง/บริการชัดเจน ทำได้เลย |

### 3. ความพร้อมของข้อมูล (Data) — 25%
| คะแนน | ความหมาย |
|---|---|
| 1 | แทบไม่มี — ต้องเริ่มเก็บข้อมูลใหม่ทั้งหมด |
| 2 | น้อย — มีบ้างแต่กระจัดกระจาย ไม่ครบ คุณภาพต่ำ ต้องทำความสะอาดมาก |
| 3 | ปานกลาง — มีข้อมูลพอเริ่มได้ แต่ต้องจัดระเบียบ/เติมเต็มบางส่วน |
| 4 | ดี — ข้อมูลค่อนข้างครบ คุณภาพใช้ได้ เข้าถึงได้ |
| 5 | พร้อมมาก — ครบถ้วน สะอาด เป็นระเบียบ พร้อมใช้ทันที |

### 4. ความเสี่ยง / ความซับซ้อน (Risk) — 15% (กลับด้าน — ยิ่งเสี่ยงมาก ยิ่งหักคะแนน)
| คะแนน | ความหมาย |
|---|---|
| 1 | น้อยมาก — งานตรงไปตรงมา ผลกระทบถ้าผิดพลาดต่ำ ควบคุมง่าย |
| 2 | น้อย — มีจุดต้องระวังบ้าง แต่จัดการได้ไม่ยาก |
| 3 | ปานกลาง — มีความซับซ้อน/ความเสี่ยงพอสมควร เช่น ข้อมูลสำคัญหรือหลายระบบ |
| 4 | สูง — ซับซ้อน เกี่ยวข้องหลายฝ่าย/ระบบ หรือเสี่ยงด้านข้อมูล/กฎระเบียบ |
| 5 | สูงมาก — เสี่ยงสูงมาก เช่น กระทบข้อมูลลับ ความปลอดภัย หรือกฎหมาย ต้องมีมาตรการเข้มงวด |

*(เดิม rubric นี้อยู่ในโค้ดเป็น `SLIDER_LEVELS` และใช้กับปุ่ม "ให้ AI ประเมินคะแนน" — ทั้งสองอย่างไม่มีในโค้ดปัจจุบันแล้ว)*

## ปัจจัยที่ตั้งใจ **ไม่** เอาเข้าสูตรคะแนน (และทำไม)

ระหว่างตรวจสอบข้อมูลจาก Excel ต้นทาง เจอปัจจัยหลายตัวที่ดูเกี่ยวข้องกับ "ความสำคัญ" แต่ตัดสินใจไม่ผสมเข้าสูตร:

| ปัจจัย | เหตุผลที่ไม่ผสมเข้าคะแนน |
|---|---|
| **กรอบเวลาที่ตั้งใจดำเนินการ** (Now / 1-2 / 3-5 / 6-10 / 11+ ปี) | เป็นคำถามคนละมิติกับ "ควรทำมั้ย" (คือ "ควรทำเมื่อไหร่") — ถ้าผสมกันจะตีความยาก ควรเก็บเป็น tag/ตัวกรองแยกต่างหาก |
| **ลำดับความสำคัญที่คนอื่นให้ไว้แล้ว** (เช่น ความเห็นจากผู้บริหาร/ที่ปรึกษาในไฟล์ Excel บางไฟล์) | เป็นความเห็นที่ตัดสินไว้แล้วจากคนจริง — ถ้าเอามาผสมกับคะแนนที่ระบบคำนวณเองจะเกิดการนับซ้ำ (double-count) ควรโชว์คู่กันไว้เทียบเฉยๆ |
| **งบประมาณที่ต้องใช้** | ถ้าเกี่ยวข้อง ควรสะท้อนอยู่ใน "Feasibility" อยู่แล้ว (งบสูง = ทำยากขึ้น) ไม่ควรแยกเป็นตัวแปรที่ 5 เพราะจะซ้ำซ้อนกับ Feasibility |
| **สถานะ GO / NO GO** | เป็น "ประตูกรอง" (filter) ไม่ใช่ปัจจัยคะแนน — ถ้า NO GO ก็ไม่ต้องคิดคะแนนเลยด้วยซ้ำ |
| **จำนวนหน่วยงานที่เกี่ยวข้อง** | ถ้าเกี่ยวข้อง ควรสะท้อนอยู่ใน "Risk" อยู่แล้ว (ยิ่งหลายแผนกยิ่งซับซ้อน/เสี่ยง) ไม่ควรแยกเป็นตัวแปรใหม่ |
| **ความครบถ้วนของข้อมูล use case เอง** (กรอกครบกี่ %) | เป็นเรื่องคุณภาพของ "การกรอกข้อมูล" ไม่ใช่คุณค่าทางธุรกิจของ use case — ควรเป็นคำเตือนแยกต่างหาก (เช่น badge "ข้อมูลไม่ครบ") ไม่ใช่ไปลดคะแนนธุรกิจ |

**หลักการ:** สูตร 4 ตัวแปรตั้งใจให้เรียบง่ายและโปร่งใส อธิบายให้ผู้บริหารฟังได้ในประโยคเดียว — ปัจจัยอื่นที่เจอเพิ่มเติมควรถูก "ดูดซับ" เข้าไปในการตีความ Feasibility/Risk ที่มีอยู่แล้ว (ผ่านดุลพินิจคนกรอก หรือ prompt ที่ให้ AI ประเมิน) แทนที่จะเพิ่มตัวแปรใหม่เข้าสูตรเรื่อยๆ

## คะแนนคือตัวช่วยกรองเบื้องต้น ไม่ใช่คำตอบสุดท้าย

สุดท้ายแล้วผู้บริหารยังต้องดู use case ที่คะแนนสูง/อยู่อันดับต้นๆ เองอีกที ว่าเหมาะกับสถานการณ์จริงหรือไม่ (งบ, จังหวะเวลา, นโยบายบริษัทช่วงนั้น ฯลฯ) — เป้าหมายของคะแนนคือ**ช่วยจัดลำดับให้เร็วขึ้นและสม่ำเสมอขึ้น** ไม่ใช่แทนที่การตัดสินใจของคน ดังนั้นเวลาออกแบบ UI ที่แสดงคะแนน ควรโชว์ข้อมูลประกอบ (กรอบเวลา, งบประมาณ, สถานะ GO/NO GO, ความเห็นคนอื่น ถ้ามี) ไว้ข้างๆ คะแนนด้วยเสมอ เพื่อให้ตัดสินใจรอบสุดท้ายได้ง่ายขึ้นโดยไม่ต้องแก้สูตรคะแนน
